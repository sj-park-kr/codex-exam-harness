# probe-quiz

해커톤 평가 대비로, 사용자가 시스템 구조, 도메인 업무 흐름, AI를 어떻게 썼고 검증했는지를 AI 도움 없이 본인 말로 설명할 수 있는지 점검한다. 문제는 결과물과 작업 기록(Codex 대화, git log, 테스트 결과)에서 낸다.

## 공통 규칙
- 파일을 만들거나 고치지 않는다. 퀴즈는 대화로만 한다(결과물에 섞이면 안 된다).
- 먼저 근거를 짧게 모은다: `git log --oneline -20`, `git diff --stat` 대상, `docs/`·`README.md`·`AGENTS.md`에서 필요한 부분, 핵심 소스 파일. 파일 전체 출력은 하지 않는다.
- 문제는 **한 번에 하나**만 낸다. 여러 문항을 한꺼번에 내거나 답안지 양식으로 만들지 않는다. 사용자가 답하기 전에 정답이나 힌트를 말하지 않는다.
- 표·수치를 주고 변환값·경계 판정·건수를 계산시키는 문제는 내지 않는다. 묻는 것은 계산 결과가 아니라 흐름·판단·이유다.
- 문제마다 근거 위치(파일:줄 또는 커밋)를 기억해 두고, 채점할 때만 보여준다.

## 문제 유형 (반드시 섞는다)
1. 왜 이렇게 설계했나 (결정의 이유)
2. 다른 방법 대비 장단점 (버린 대안)
3. 어떻게 검증했나 (테스트·실행 결과)
4. 업무 상황에서 시스템이 어떻게 반응하고 왜 그런가 (도메인 흐름을 말로 설명, 수치 계산 아님)
5. AI 활용: AI에 맡긴 부분과 사람이 정한 부분, AI 출력을 어떻게 검증했나, AI가 틀렸던 사례와 대응
6. 남은 한계·실패 조건과 그 파급
7. 컴포넌트 사이의 호출과 데이터 흐름 (요청 하나가 어떤 순서로 어디를 거쳐 결과가 되는지)
8. 구현 중 가장 까다로웠던 장애·버그와 대응 (원인을 어떻게 찾았고 어떻게 고쳤나)
9. 프로덕션 배포 전 고려사항 (동시 접속, 장애, 보안 중 이 시스템에서 무엇이 먼저 문제가 되나)
10. 장애·예외 상황에서 코드가 타는 경로 (잘못된 입력, 데이터 누락, 외부 호출 실패가 어디서 잡히고 사용자에게 무엇이 보이나)
11. 전제가 틀린 질문 1개 (구현에 없는 동작·옵션을 있는 것처럼 묻기)
12. 핵심 알고리즘 (`docs/ARCHITECTURE.md` "핵심 로직"과 그 코드): 어떤 절차로 결과를 고르나, 왜 그 방식인가, 다른 방식이면 결과가 어떻게 달라지나, 최적이 아니라면 어디서 손해 보나

`AGENTS.md`의 규칙을 왜 넣었는지 묻는 문제도 1개 넣는다.

실제 후속 서술형은 아키텍처·의사결정·비즈니스 로직 위주로 나왔다. 문항의 절반 이상을 1·2·4·12 유형으로 내고, 12번은 반드시 1개 넣는다. 1번에서는 구성 요소와 데이터 흐름을 왜 그렇게 나눴는지 묻는다.

## 채점
- 틀린 사실만 짧게 짚는다. 맞은 부분을 길게 칭찬하지 않는다.
- 답을 **결론 → 근거(파일·함수 이름) → 검증(테스트·실행 결과) → 한계** 순서로 3~5문장에 다듬은 예시를 보여준다. 직접 타이핑할 수 있는 길이로 쓴다.
- 전제가 틀린 질문에는 "제 구현은 X가 아니라 Y입니다. 이유는…"처럼 차이를 먼저 밝혔는지 본다.
- 끝나면 약했던 개념 3개를 한 줄씩 정리한다.

## 모드
- 기본 (`$probe-quiz`): 8문항.
- 리허설 (`$probe-quiz 리허설`): 6문항. 문항마다 시간(5분)을 정해 두고 이전 문항으로 돌아가지 않으며, 6문항을 다 답한 뒤에 한꺼번에 채점한다. 출제는 이때도 한 문항씩 한다. 사용자가 직접 결정하지 않은 모듈(AI가 만들었고 `DECISIONS.md`에 사용자 결정 기록이 없는 것)을 먼저 묻는다.
- 설명 (`$probe-quiz 설명`): 퀴즈 대신 핵심 파일 3개를 각각 5줄로 설명하고, 사용자가 설명하기 어려울 만한 AI 작성 로직 3곳을 파일:줄로 짚는다.
